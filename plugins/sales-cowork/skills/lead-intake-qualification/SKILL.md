# 銷售線索接收與資格評估

## 概述

把單一線索或最多十筆的限定批次轉成證據導向 qualification brief。不得僅依職稱、公司規模或語氣推斷 Budget、Authority、Need、Timing、Consent 或 Fit。

## 適用情境

- 檢視指定期間的新詢問、活動名單或轉介。
- 判斷線索為 `進一步確認`、`培養`、`不符合` 或 `未知`。
- 找出重複線索、缺少資料及適合的內部 Owner。
- 準備首次回覆或 Planner 工作預覽。

## 不適用情境

- 大量或自動化行銷序列。
- 既有商機的 Deal Strategy。
- 將模糊意向直接轉成 Forecast 或 Pipeline 承諾。

## 快速開始

1. 確認 intake 來源、時間範圍與最多十筆的批次上限。
2. 用 `ask` 找出線索訊息、相關公司、人員與既有互動。
3. 用 `search_paths`、`get_schema`、`fetch` 驗證訊息、People、register 與重複項目。
4. 分開記錄外部陳述、內部事實、qualification 推論與未知。
5. 每筆只提出一個最安全下一步；回覆或資料更新都先預覽並取得核准。

## 核心流程

### 階段一：界定 Intake

- 指定 Outlook、Teams、核准的 Excel／SharePoint register 或使用者提供的來源。
- 指定時間、客群或 Owner；預設不跨越要求範圍。
- 沒有核准 register 時仍可完成唯讀評估，相關欄位標示 `無法取得`。

### 階段二：身分與重複檢查

- 以寄件地址、公司網域、姓名及可存取的人員資料做 entity resolution。
- 不把相同姓名自動視為同一人。
- 建立資料前，以 `fetch` 檢查相同 Email、公司與近期詢問。

### 階段三：證據式 Qualification

逐筆整理明確的業務問題、已知角色、期限、與核准 ICP／服務範圍的符合證據，以及仍需確認的 Budget、Authority、Need、Timing、Consent 與採購條件。

- `進一步確認`：有明確問題及合理符合證據，但仍需 discovery。
- `培養`：可能相關，但時機或需求證據不足。
- `不符合`：只有具明確排除證據時使用。
- `未知`：資訊不足，不能合理判定。

### 階段四：下一步與執行

回覆只使用 Work IQ 明確支援的 `do_action` URL；register 或 Planner 變更先完成 path/schema discovery。每項動作顯示對象、內容、目的、欄位與來源，再等待核准。

### 階段五：建立最小 Discovery 路徑

對每筆非「不符合」線索，只提出一個最能降低不確定性的下一步。問題應直接驗證業務問題、受影響範圍、目前做法、期望結果、決策參與者或時間事件，不要一次寄出完整問卷。

依線索成熟度處理：

- 有明確問題但缺少影響：詢問問題造成的實際後果及受影響對象。
- 有需求與時程但聯絡人角色不明：確認其參與方式及還有哪些人需要加入。
- 只有產品詢價：先確認使用情境、數量／範圍與採購事件，不直接判定有 Budget。
- 只有活動名單或名片：若沒有同意或互動背景，不推定可進行行銷聯繫。
- 已存在 Account 或 Opportunity：提供給現有 Owner 的證據與建議，不建立重複項目。

## Qualification 判斷規則

### 可確認的 Fit

Fit 必須來自核准的 Ideal Customer Profile、服務範圍、地區、技術或商務條件。沒有核准標準時，描述觀察到的符合與不符合，不自行建立分數。

### 不可直接推斷的項目

- 公司規模不等於 Budget。
- 高階職稱不等於實際 Decision Authority。
- 詢價不等於購買時程。
- 下載內容、參加活動或接受連線不等於同意後續行銷。
- 使用競爭產品不等於有替換意願。
- 內部轉寄或主管關注不等於 Sales accepted lead。

### Disposition 的充分條件

| 判斷 | 必須具備 | 後續處理 |
|---|---|---|
| 進一步確認 | 可辨識問題、合理 Fit 證據及可執行的 Discovery 路徑 | 指定一個 Discovery 下一步 |
| 培養 | 主題可能相關但沒有近期事件或問題證據 | 定義重新檢視的事件或日期 |
| 不符合 | 有明確排除條件、重複歸屬或無法服務的證據 | 記錄原因，不使用貶抑語言 |
| 未知 | 缺少足以判斷的核心資訊 | 提出一個最小驗證問題 |

## 完整產出要求

每筆線索需產出完整的 Qualification record，而不是一句評語：

1. 身分與來源：姓名、公司、可驗證聯絡方式、取得時間、來源及 Consent 狀態。
2. 對方原始陳述：保留需求、問題或詢問，不改寫成已確認 Opportunity。
3. 內部背景：既有 Account、互動、Owner、重複紀錄與相關工作。
4. 已知與未知：分開列出，不以空白或預設值掩蓋。
5. Qualification：判斷、直接證據、信心與不能下結論的部分。
6. 下一步：對象、目的、唯一核心問題、建議 Owner 及完成標準。

批次處理時，先列重複、資料衝突與需要人工確認的項目，再列逐筆結果。不得為了排序而捏造 Lead score。

## 回覆草稿規則

只有使用者要求時才附首次回覆草稿。草稿要：

- 對對方的實際詢問做出回應。
- 清楚說明下一步及需要對方補充的一個核心資訊。
- 不宣稱已通過 Qualification、不承諾價格、能力、時程或資源。
- 使用對方語言與合適的專業程度，不暴露內部評分或 Account 註記。

## 停止條件

- 超過十筆時先完成去重與分批建議，不假裝全部已深度評估。
- 缺少 Consent 或聯繫依據時，不進入 Outreach 執行。
- 找到既有 Opportunity 時停止新建並交由現有 Owner。
- 來源含敏感個資且使用目的不明時，只保留必要欄位並停止擴散。

## 輸出格式

| 線索 | 外部陳述 | 內部事實 | Qualification | 缺少資訊 | 建議 Owner | 下一步 | 來源 |
|---|---|---|---|---|---|---|---|
|  |  |  | 進一步確認／培養／不符合／未知 |  |  |  |  |

結尾：`唯讀評估完成`、`等待核准`、`已核准並完成` 或 `受政策阻擋`。

## 使用者溝通與完成檢查

- 直接交付逐筆 Qualification 結果與下一步，不以來源摘要取代評估。
- 使用一般 Sales／Business 語言；內部工具、path、schema 與 payload 不出現在結果中。
- 不輸出隱藏思考；只說明支持判斷的證據、未知與會改變判斷的資訊。
- 每筆已完成身分解析、Duplicate、Consent、Fit、Disposition 與最小 Discovery 檢查。
- 回覆草稿與實際寄送狀態必須分開。

## Work IQ 工具規則

- `ask` 尋找跨工作負載背景。
- `search_paths`、`get_schema`、`fetch` 驗證來源、重複資料與可寫入欄位。
- `create_entity`、`update_entity` 只在使用者核准精確 preview 後執行。
- `do_action` 只使用 Work IQ 回傳的完整 action URL。

## 範例

**輸入：**「幫我評估今天收到的五筆詢問。」

**正確行為：**限定今天及五筆，先去重，分開外部說法與內部事實，未知欄位不猜測；不直接寄出回覆。

## Guardrails

- 不從職稱或公司規模推斷 Budget、Authority 或購買意圖。
- 不把公開資訊當成對方同意被聯繫的證據。
- 不批次寄送未核准訊息。
- Tenant policy 拒絕後不得換工具重試。

## 常見問題

| 問題 | 處理方式 |
|---|---|
| 同名或共用信箱 | 要求唯一識別資料，不合併紀錄。 |
| 無核准 intake register | 完成唯讀 brief，register 欄位標示 `無法取得`。 |
| 找到既有商機 | 停止新建，提供重複證據並轉交既有 Owner。 |
| 資訊不足 | 使用 `未知`，提出一個可驗證問題。 |
