# 市場與競爭研究

## 概述

把市場或競爭問題轉成可追溯的 Evidence Brief 與可在客戶對話中驗證的 Sales Hypotheses。內部 Work IQ 證據、公開來源、推論與未知必須分開呈現。

## 適用情境

- 指定產業變化對客戶的可能影響。
- 特定競爭者、替代方案或 Build-vs-Buy 比較。
- 建立客戶對話用 Battlecard 或 objection evidence。
- 驗證明確的 Account／Market hypothesis。

## 不適用情境

- 只有公司名稱而沒有研究問題。
- SEO、GEO、廣告或內容排名分析。
- 將公開新聞直接當成客戶購買意圖。
- 內部 Account 歷程 → `account-research`

## 快速開始

1. 確認研究對象、具體問題、決策用途、時間範圍與是否需要公開研究。
2. 以 `ask` 或支援的 `call_function` 蒐集內部企業證據。
3. 對重大內部敘述使用 `search_paths`、`get_schema`、`fetch` 驗證。
4. 只有使用者明確要求時才執行 Deep Research，記錄發布日期及直接來源。
5. 產出 Evidence、Comparison、Implications、Hypotheses 與 Unknowns。

## 核心流程

### 階段一：研究問題

問題必須包含對象、比較或變化、時間範圍及預期銷售用途。只有「研究某公司」時，先要求具體研究問題，不生成百科式簡介。

### 階段二：來源分層

1. **內部證據**：Microsoft 365 中的客戶陳述、會議、文件與內部分析。
2. **公開證據**：使用者明確要求後，由 Deep Research 取得的原始或權威來源。
3. **推論**：從證據推導、仍待驗證的銷售含意。
4. **未知**：來源無法回答或超出權限的部分。

不得以第三方摘要取代可取得的原始來源，也不得把不同發布日期的資料當成同一時點。

### 階段三：比較與影響

依問題比較客戶成果、能力、限制、導入條件、風險、商務模型與治理。只比較有證據支撐的維度；資料不對稱時標示 `證據不足`。

### 階段四：輸出

| 發現 | 來源類型 | 來源 | 日期 | 信心 |
|---|---|---|---|---|
|  | 內部／公開 |  |  |  |

| 維度 | 證據 | 銷售影響 | 待驗證問題 |
|---|---|---|---|
|  |  |  |  |

最後列出 `已確認結論`、`Sales Hypotheses`、`客戶確認事項` 與 `未知`。未要求公開研究時顯示 `未要求公開研究`。

### 階段五：形成可用於銷售對話的觀點

每個 Sales Hypothesis 必須由「證據 → 對客戶可能的影響 → 需要驗證的問題」組成。不要把研究結果直接轉成產品推銷句。若客戶的實際環境、優先事項或替代方案仍未知，假設必須保持開放。

可使用的比較面向包括：

- 對客戶 Business outcome 的影響。
- 核心能力及明確限制。
- 導入前提、整合、遷移與營運負擔。
- Security、Privacy、Compliance 與治理要求。
- 商務模式、公開價格邏輯與總持有成本；非公開價格保持未知。
- Partner／Delivery 能力、支援方式及可驗證案例。
- Roadmap 只引用官方已公開內容，不把傳聞當承諾。

### 階段六：建立 Battlecard

只有使用者要求 Battlecard 時才產出，並包含：

1. 客戶可能在意的三個決策面向。
2. 我方有證據支持的差異化能力。
3. 競爭者已驗證的優勢與限制。
4. 不應宣稱或目前無法驗證的內容。
5. 客戶常見問題與以證據為基礎的回應。
6. 用於 Discovery 的問題，而不是操弄式話術。
7. 來源與發布日期。

不得使用貶低競爭者、無來源的 Fear／Uncertainty／Doubt、虛構客戶案例或暗示未公開 Roadmap。

## 研究品質規則

- 先使用官方產品文件、公司揭露、法規、原始研究或具名客戶來源，再使用可信二手分析。
- 對可能快速變動的產品能力、價格、公司狀態與法規，必須確認發布及觀察日期。
- 數字需保留單位、期間、母體與方法；缺少任何一項時降低信心。
- 比較必須使用同一範圍與時點；方案層級不同時不可直接宣稱勝負。
- 市場規模若沒有可驗證方法，只能稱為來源估計，不可自行拼接成精確 TAM。
- 每項研究事實需能追溯到直接來源；搜尋結果摘要不是最終引用。

## 完整產出要求

先回答使用者的研究問題，再提供支持內容：

1. **Executive finding**：最多五項，每項為可直接用於決策的結論。
2. **比較範圍**：對象、版本、地區、客群、時點及排除項目。
3. **Evidence table**：主張、來源類型、直接來源、日期、信心與限制。
4. **Comparison**：只放對客戶決策有意義且證據對稱的維度。
5. **Sales implications**：對 Account／Opportunity 的可能影響，與事實分開。
6. **Sales hypotheses**：每項附驗證問題及會改變判斷的回答。
7. **Unknowns and contradictions**：說明缺口，不用一般性結論補齊。
8. **Recommended next conversation**：如何在客戶對話中驗證，不直接對外發布。

## 停止條件

- 沒有明確研究問題時，只協助建立問題，不產出百科式報告。
- 公開研究未被要求時，不自動瀏覽網路或混入外部資料。
- 來源無法支持比較時，回覆證據不足及需要取得的資料。
- 要求取得非公開競爭情報、繞過存取或使用不當來源時停止。

## 使用者溝通與完成檢查

- 先回答研究問題，再提供 Evidence、Comparison、Implication 與驗證問題。
- 對外使用一般商務語言；不顯示 tool、path、schema、內部檢索方式或思考過程。
- 內部證據、公開來源、推論與未知已清楚分隔。
- 每項重大主張有直接來源與日期，快速變動資訊已按目前時點驗證。
- Battlecard 不含無來源攻擊、虛構優勢或不當競爭情報。

## Work IQ 工具規則

- `ask`：內部跨工作負載推理。
- `call_function`：只使用目前支援的企業搜尋或計算函式。
- `fetch`：驗證精確內部實體；先執行 path/schema discovery。
- 不執行任何寫入或客戶互動。

## 範例

**輸入：**「比較競爭者 X 與我們在治理能力上的差異，供 Contoso 會議使用，並做公開研究。」

**正確行為：**界定比較時點，分開內部與公開證據，將會議說法寫成待驗證 hypothesis，而非客戶既定需求。

## Guardrails

- 公開研究必須由使用者明確要求。
- 不捏造競爭者能力、價格或 Roadmap。
- 不把公開新聞視為客戶已確認的 Budget、Intent 或 Timeline。
- 不發送 Battlecard、更新 Account artifact 或對外發布結果。

## 常見問題

| 問題 | 處理方式 |
|---|---|
| 問題太寬 | 要求一個決策用途與研究問題。 |
| 來源日期不同 | 保留日期並說明不可直接比較。 |
| 只有二手來源 | 降低信心並標示來源限制。 |
| 競爭資訊無法驗證 | 標示 `未知`，提出驗證問題。 |
