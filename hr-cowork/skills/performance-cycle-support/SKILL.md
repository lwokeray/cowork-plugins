# Performance Cycle Support

## 概述

把分散的目標、成果、回饋與 Check-in 紀錄整理為平衡、可追溯且與角色期望對齊的 Performance Review 材料。Agent 協助辨識證據、缺口、Recency／Visibility／Attribution 等偏差、準備校準問題與發展計畫；Rating、Promotion、Compensation、PIP、Discipline 與 Termination 均由授權 Human owner 決定。

## 適用情境

- 撰寫 Self-review 或 Manager review 初稿。
- 對照 Goals、Role expectations、成果、行為與 Development commitments。
- 整理 1:1、Project feedback、Stakeholder feedback 與可驗證工作成果。
- 準備 Calibration pack、Score／Narrative consistency 與 Bias check。
- 建立下一週期目標、支持與 Check-in 計畫。

## 不適用情境

- 不以 Email／Teams 活動量、登入、會議時間、回覆速度、工時或 Presence 推斷績效與投入度。
- 不推斷人格、忠誠、態度、情緒、健康、家庭或其他敏感屬性。
- 不由 Agent 自動評等、排序、強制分布、預測離職、建立 PIP 或建議終止。
- 不把未驗證傳聞、單一近期事件或他人工作歸因給員工。

## 快速開始

1. 驗證 Employee、Role／Level、Review period、Manager、Goals、Competency、Rating scale 與政策版本。
2. 用 `ask` 尋找經授權的成果、Check-in、Feedback 與 Commitment，再用 `fetch` 驗證原始來源。
3. 建立 `Goal／Expectation → Evidence → Outcome → Employee contribution → Gap／Context` 矩陣。
4. 分開事實、Self-report、Manager observation、Stakeholder feedback、Inference 與 Unknown。
5. 檢查 Recency、Visibility、Attribution、Similarity、Halo／Horns、Leave／Accommodation contamination 與標準不一致。
6. 產生 Review Draft、Calibration questions 與 Development plan；等待 Human rating 與核准後才寫入系統。

## 核心流程

### 階段一：標準與期間鎖定

在擷取證據前確認 Review start／end、Role、Level、Goals、Weight、Competency、Rating anchors、Eligibility 與 Manager。Mid-cycle role change、Manager change、Leave、Transfer 或 Goal change 要分段處理，不能用期末角色標準回溯整期。

若 Goals 未正式確認，Agent 可整理實際交付與 Role expectations，但不能假裝存在已核准 KPI。Rating scale 必須使用組織原始定義，不自行轉換 1–5、百分比或常態分布。

### 階段二：證據收集邊界

只收集與已知 Goals／Role expectations 相關且使用者有權限的資料。可用來源：正式 Goals、Project deliverables、Decision／artifact、客戶或 Stakeholder 已授權回饋、Incident／quality records、Learning completion、員工自評與 1:1 commitments。

不可用作直接績效證據：私人聊天、非必要活動 metadata、Presence、工時推算、社交互動、敏感 Case、Leave／Accommodation、健康或家庭資訊。公開表揚可作輔助來源，但仍需說明具體貢獻。

### 階段三：Contribution 與 Outcome

每項成果記錄：Context、Goal、Employee role、Actions／Decisions、Scope、Stakeholders、Outcome、Evidence link、Constraints、Collaborators。清楚區分 `Owned／Led／Implemented／Supported／Contributed／Proposed`，不把團隊成果全部歸給單一員工，也不因低可見度忽略後台工作。

數字需有來源、口徑與期間。若沒有量化結果，可使用可觀察變化：流程完成、Risk reduced、Decision enabled、Quality improved、Stakeholder adoption、Issue resolved。不要捏造百分比或 ROI。

### 階段四：平衡回饋

Review narrative 應包含：已展現的影響、持續優勢、具體成長區、支持與下一步。Development feedback 使用 `觀察到的行為 → 工作影響 → 期望行為 → 支援／Checkpoint`，避免「態度不好、缺乏熱情、不是 Leader material」等人格標籤。

負面回饋若首次出現在期末 Review，標示 Process risk，要求 Manager 確認是否曾及時溝通與提供支持。Agent 不自行刪除事實，但要指出程序與公平性問題。

### 階段五：Bias 與一致性檢查

逐項檢查：

- **Recency**：是否只看最近事件。
- **Visibility**：是否只獎勵高曝光工作。
- **Attribution**：團隊成果／問題歸屬是否正確。
- **Similarity／Affinity**：是否因背景、風格、興趣相似而偏好。
- **Halo／Horns**：單一強項／失誤是否支配全部評價。
- **Leave／Accommodation contamination**：依法或政策受保護的缺勤／調整是否被當負面。
- **Standard shift**：是否對不同員工使用不同 Level 或未事先告知標準。

只指出風險與需要人工校準之處，不依敏感屬性計算個人分數。

### 階段六：Calibration Pack

Calibration 應以 Role／Level 與證據為中心，不用個人喜好或預算倒推 Rating。每位員工只顯示完成校準所需資料；敏感 Case、Leave、Accommodation、醫療、家庭或薪酬歷史不納入一般 Pack。

若 Rating 與 Narrative／Anchor 不一致，指出差異並要求 Manager 說明或修改；Agent 不替 Manager 改分。若組織要求 Forced distribution，依正式政策由 HR owner 管理，不由 Agent 自動重排。

### 階段七：決定與寫入

Human Manager／Calibration owner 作成 Rating、Promotion／Compensation recommendation 或 Performance action。Preview 顯示 Rating、Narrative、Goals、Development、Acknowledgement、Owner、Approval 與可見性。PIP、Discipline 或 Termination 使用專屬 ER／Legal 流程，不從一般 Review 直接執行。

## 完整產出要求

1. Employee、Role／Level、Period、Manager、Goal／Competency／Scale version。
2. 每項 Goal／Expectation 的證據、Contribution、Outcome、Context、Source 與 Gap。
3. Strength、Development、Support、Checkpoint 與下一週期建議。
4. Bias／process risks、Rating／Narrative alignment 與 Calibration questions。
5. Human rating／decision 欄位、Dissent、Approval 與實際寫入狀態。

## 輸出格式

### Performance Evidence Matrix

| Goal／Expectation | Employee contribution | Outcome | Evidence | Context／Gap | Manager validation |
|---|---|---|---|---|---|

### Review Draft

- **Impact delivered**：以具體成果與角色描述。
- **Strengths to continue**：工作行為與價值。
- **Development focus**：觀察、影響、期望、支持、Checkpoint。
- **Context and constraints**：只列工作相關且必要資訊。
- **Human rating**：`待 Manager／Calibration 決定`。

### Calibration Checks

| 風險／不一致 | 證據 | 需要哪位 Owner 處理 | 狀態 |
|---|---|---|---|

## 停止條件

- Role、Period、Goals、Rating scale 或 Manager 不明時，不產生 Rating 建議。
- 使用者要求以監控、Presence、工時、Leave、Accommodation 或敏感屬性評估時停止。
- PIP、Discipline、Promotion、Compensation 或 Termination 沒有專屬 Human process 時不執行。
- Rating 與 Evidence 衝突或首次重大負面回饋未經處理時，標示 Calibration／HR review。
- Tenant policy 拒絕後不得改用其他資料來源擴張監控。

## 使用者溝通與完成檢查

- 直接交付 Evidence Matrix 與可用 Review Draft，不把資料蒐集摘要當結果。
- 使用具體工作行為與影響，避免人格、動機、忠誠或情緒判斷。
- 檢查數字、Contribution、Period、Goal、Role 與來源一致。
- 檢查 Human owner 明確，Agent 沒有自動填 Rating／Decision。
- 不輸出隱藏思考，只列證據、未知、偏差風險與校準問題。

## Work IQ 工具規則

- `ask` 尋找 Goals、成果、Feedback、Check-in 與正式 Review materials。
- `search_paths` 定位核准 Performance system、Role framework 與模板。
- `get_schema` 在任何 Review entity 寫入前取得欄位與可見性。
- `fetch` 驗證完整 Evidence、版本、Human rating 與 Approval。
- `create_entity`、`update_entity` 只在 Human decision 與精確 Preview 核准後使用。
- `do_action` 只傳送已核准 Review／Check-in 通知。
- 不使用工具建立員工活動監控或繞過受限 Case 邊界。

## 範例

**輸入：**「幫我看誰每天最晚下線、Teams 最少發言，排出績效後 10%。」

**正確行為：**不使用活動量、下線時間或強制排名；回到核准 Goals、Role expectations、具體成果與工作行為，建立 Evidence Matrix，Rating 由 Manager／Calibration owner 決定。

## Guardrails

- 不監控員工活動或以 Presence、工時、郵件／聊天量推斷績效。
- 不自動評等、排序、預測離職、建立 PIP、處分或終止。
- 不使用 Leave、Accommodation、健康、家庭或其他敏感資訊。
- 不捏造 KPI、成果、Ownership、數字或回饋。
- 不將草稿或 Calibration note 寫入正式 Record，除非 Human owner 核准。

## 常見問題

| 問題 | 處理方式 |
|---|---|
| 目標中途改變 | 分段列出有效期間與核准版本。 |
| 沒有量化結果 | 使用可觀察 Outcome，不捏造數字。 |
| Manager 只給人格評語 | 改寫為需要具體觀察、工作影響與期望行為。 |
| Rating 與 Narrative 不符 | 標示 Calibration issue，由 Manager 說明或調整。 |
| 期末才出現重大負面回饋 | 標示 Process risk，交 HR／Manager 處理。 |
