# Learning & Development Plan

## 概述

將職務需求與可驗證能力差距轉為能在工作中應用的發展計畫。計畫包含目標能力、Baseline、學習活動、實作任務、Manager／Mentor 支援、時間、成本、Accessibility、Evidence 與 Review cadence。完成課程不等於具備能力；成果必須透過工作相關的實作與觀察驗證。

## 適用情境

- 個人 Development plan、Career path、Promotion readiness 支援。
- 團隊 Upskilling／Reskilling、技術或業務能力提升。
- Mandatory／Compliance training 計畫與逾期追蹤。
- 建立課程、Mentoring、Shadowing、Stretch assignment 與 Practice 組合。
- 檢查學習完成率、應用證據、阻塞與下一步。

## 不適用情境

- 不以人格類型、學習風格測驗、年齡、健康、家庭或其他敏感屬性決定能力與發展機會。
- 不把未參加非必要社交活動或課外學習當績效問題。
- 不以課程完成自動核准 Promotion、Certification、Access 或工作資格。
- 不用一般 Training plan 取代 PIP、Discipline、Accommodation 或 ER 流程。

## 快速開始

1. 確認對象、Role／Level、Target outcome、期間、Manager、能力模型與可用資源。
2. 用 `ask` 找出 Goals、Performance evidence、Self-assessment、Project needs、既有訓練與認證。
3. 用 `search_paths`、`get_schema`、`fetch` 驗證正式 Learning catalog、Policy、Prerequisite、Cost、Schedule 與 Completion record。
4. 建立 `Capability → Baseline evidence → Target behavior → Learning／Practice → Evidence → Review`。
5. 平衡 Formal learning、Social learning 與 On-the-job practice，指定時間與支援。
6. 先交付 Plan；報名、購買、指派或更新完成狀態需 Preview 與核准。

## 核心流程

### 階段一：需求與成功定義

從業務／職務成果開始，不從課程清單開始。釐清：需要誰在何種情境做出什麼不同工作行為、目前證據、目標 Level、最晚使用時間、失敗風險與支持條件。

將需求分類為 Knowledge、Skill、Judgment、Process、Tool、Relationship／Influence 或 Required credential。不是所有績效問題都可用訓練解決；若根因是權限、流程、資源、目標衝突、Manager support 或角色設計，應標示非學習措施。

### 階段二：Baseline 與 Gap

Baseline 來源可包含工作樣本、Manager observation、Self-assessment、Assessment、Certification、Project outcome 或已核准 Feedback。分開：

- 已證明能力。
- 有相鄰證據但需要轉移。
- 未取得證據。
- 因機會不足而非能力不足。
- 非 Learning root cause。

`未取得證據` 不等於缺乏能力。不得從年齡、教育品牌、口音、工作風格或活動量推斷學習能力。

### 階段三：學習路徑設計

每項 Target capability 搭配：

- **Learn**：精選課程、閱讀、Workshop、Lab 或 Policy briefing。
- **Observe**：Mentor、Shadowing、Peer review、示範案例。
- **Practice**：安全、範圍明確的真實或模擬工作任務。
- **Feedback**：具名 Reviewer、Rubric、時點與可操作回饋。
- **Apply**：在實際角色成果中使用並留下 Evidence。

避免一次堆積大量課程。每個活動要說明與 Target behavior 的直接關係、Prerequisite、時間、成本、語言、時區、Accessibility、資料安全與完成方式。

### 階段四：Mandatory Training

Mandatory 項目必須來自正式 Policy／Role／Location／Access requirement。記錄 Assignment source、Due date、Validity／renewal、Provider、Completion evidence、Exception／Accommodation route。不要把過期或不適用課程自動指派給所有人。

逾期提醒遵循核准 Cadence；Completion 未同步時先驗證 Provider record，不直接標示員工未完成或不配合。

### 階段五：Development 與公平機會

Stretch assignment、Mentoring、Conference、Certification budget 與 Promotion-prep 需透明條件與 Owner。檢查機會是否受 Manager visibility、時區、Location、Leave／Accommodation 或非必要社交參與影響。Agent 不依敏感群體自動調整個人機會，但應指出標準不一致或 Access barrier 供 HR／Manager 審查。

### 階段六：成效評估

區分四層：

1. Participation／Completion：是否完成，不代表能力。
2. Knowledge／Skill evidence：Assessment、Lab、Work sample。
3. Behavior application：是否在工作中使用目標行為。
4. Outcome：品質、速度、風險、採用或其他已定義工作結果。

建立 Baseline、Target、Evidence source、Reviewer、Review date 與限制。不要將簡單滿意度當業務成效，也不捏造 ROI。

### 階段七：執行與更新

任何 Course assignment、Enrollment、Purchase、Calendar、Mentor invitation、Access 或 Learning record update 都需顯示 Preview。執行後驗證 Enrollment／Completion 狀態；`Assigned`、`Enrolled`、`Attended`、`Completed`、`Demonstrated` 必須分開。

## 完整產出要求

1. Learner／team、Role、Target outcome、Period、Manager、Policy／capability version。
2. Capability Baseline、Target behavior、Gap、Root cause 與 evidence limits。
3. Learn／Observe／Practice／Feedback／Apply 的完整路徑。
4. Owner、Time、Cost、Prerequisite、Accessibility、Risk 與 support。
5. Mandatory／optional 區分、Due、renewal 與 exception route。
6. Evaluation framework、Review cadence、Status 與核准動作。

## 輸出格式

### Development Plan

| Capability | Baseline | Target behavior | Learning／Practice | Support | Evidence | Review date | Status |
|---|---|---|---|---|---|---|---|

### Non-learning Actions

| Root cause | Needed change | Owner | Deadline | Relationship to plan |
|---|---|---|---|---|

### Completion and Application

以 `Assigned／Enrolled／Attended／Completed／Demonstrated／Outcome observed` 分開記錄。

## 停止條件

- Role outcome、Target behavior 或 Baseline evidence 不明時，不把課程清單當計畫。
- 問題根因不是能力／知識時，標示非 Learning action，不強制指派訓練。
- 使用者要求依人格、年齡、健康、家庭或敏感屬性分配機會時停止。
- 購買、報名、Access、Travel 或 Certification 有成本／政策影響時等待授權核准。
- Tenant policy 拒絕後不得以私人帳號或外部未核准平台繞過。

## 使用者溝通與完成檢查

- 直接交付 Development Plan，不以推薦課程摘要取代實作與成效。
- 檢查每個活動連結 Target behavior、Owner、Evidence 與 Review。
- 檢查 `未取得證據` 未被當作能力不足，完成課程未被當作已具能力。
- 檢查 Mandatory 來源、適用性、Due 與 Accessibility。
- 不輸出隱藏思考，只列證據、Gap、假設與可審查設計。

## Work IQ 工具規則

- `ask` 尋找 Role、Goals、Evidence、Learning materials、Mentor 與專案機會。
- `search_paths` 定位正式 Catalog、Policy、Capability model 與 Learning record。
- `get_schema` 在 Assignment／record 寫入前取得欄位。
- `fetch` 驗證 Course version、Prerequisite、Cost、Schedule、Completion 與政策。
- `create_entity`、`update_entity`、`do_action` 只在精確 Preview 與核准後使用。
- 不以學習平台活動 metadata 建立績效或人格推斷。

## 範例

**輸入：**「他比較資深，應該學不動 AI，安排基礎課就好。」

**正確行為：**不從年齡／資歷推斷學習能力；依角色成果、現有工作證據與自評建立 Baseline，再設計適當 Learn／Practice／Feedback 路徑。

## Guardrails

- 不以人格、年齡、健康、家庭、口音或其他敏感資訊決定發展機會。
- 不把訓練完成自動等同能力、資格、Promotion 或績效。
- 不用 Training plan 取代正式 Performance／ER／Accommodation 流程。
- 不捏造課程、成本、認證、完成或成效資料。
- 不未經核准購買、報名、指派或對外分享員工資料。

## 常見問題

| 問題 | 處理方式 |
|---|---|
| 不知道能力差距 | 先設計小型 Work sample／Observation 取得 Baseline。 |
| 課程太多 | 只保留與 Target behavior 直接相關項，加入實作與回饋。 |
| 完成紀錄未同步 | 驗證 Provider／source，不直接標逾期。 |
| 根因是沒時間或權限 | 建立 Non-learning action，由 Owner 解決。 |
| 需要 Promotion plan | 對齊正式 Level evidence，不承諾 Promotion。 |
